The problem with "someone emails it every week"

😣 Manual & fragile

A person remembers (or forgets) to send the Monday report. PTO, sick days, and handovers create gaps no one notices.

🕵️ No audit trail

"Did we send the Q2 pack? To whom? With which attachment?" The proof lives in someone's Sent folder — if it still exists.

❓ No follow-up

You need the CFO to revert with approval. Today, chasing that is a manual scan of the inbox.

mailflow turns this into a reliable, auditable, self-tracking pipeline.

Three jobs, done automatically

1 Send on schedule

Define jobs in YAML — recipients, subject/body templates, attachments, and an interval / daily / weekly / once schedule. Fires via cron or a long-running daemon.

2 Archive every message

A verbatim .eml copy of each send is written to a path you choose — an instant, opens-in-Outlook audit record.

3 Track the revert

Each message's status is recorded: sent → replied. Replies are matched automatically over IMAP, or marked manually.

Live demo

Scenario: Acme Corp weekly financials

A service account finance-automation@acme.example must, every Monday 08:00:

  • e-mail the weekly figures (CSV attached) to the CFO & Controller, cc Audit;
  • keep an audit copy of exactly what went out;
  • flag whether the CFO reverted with approval.

The demo runs the full lifecycle for real against a local capture relay — no internet, no live mailbox. Run it yourself:

bash demo/run_demo.sh

# the job definition (mailflow.yaml) jobs: - name: weekly-financials to: [cfo@acme.example, controller@acme.example] cc: [audit@acme.example] subject: "Acme Weekly Report - {date}" attachments: [reports/weekly_*.csv] schedule: every: weekly weekday: mon at: "08:00"

Validate → preview → send (real output)

$ mailflow validate ✓ config OK — 1 job(s): • weekly-financials: 2 recipient(s), weekly on mon at 08:00; next: 2026-06-22 08:00 $ mailflow send weekly-financials --dry-run [dry-run] would send weekly-financials to cfo@acme.example, controller@acme.example, audit@acme.example (nothing written) $ mailflow send weekly-financials ✓ sent weekly-financials (id=1), saved to archive/20260619-092311_weekly-financials.eml [relay] delivered to cfo@acme.example, controller@acme.example, audit@acme.example subject: Acme Weekly Financial Report - 2026-06-19 -> inbox/received-...eml

A dry run changes nothing — no file, no record, schedule not advanced.

Revert tracking: sent → replied

$ mailflow status # right after sending id status job sent subject 1 … sent weekly-financials 2026-06-19 09:23 Acme Weekly Financial Report totals: sent=1 $ mailflow check-replies # polls IMAP; here we mark it manually $ mailflow mark-replied 1 --from cfo@acme.example ✓ marked send id=1 as replied. $ mailflow status id status job sent subject 1 ✓ replied weekly-financials 2026-06-19 09:23 Acme Weekly Financial Report ↳ revert from cfo@acme.example at 2026-06-19 09:23 totals: replied=1

Two ways to run it

Cron / Task Scheduler

# check every 15 min; mailflow fires only due jobs */15 * * * * cd /opt/mailflow && \ python -m mailflow run >> mailflow.log

OS owns the timer; mailflow decides what's due. Catches up a missed slot.

Long-running daemon

$ python -m mailflow daemon mailflow scheduler started (poll every 60s) # fires jobs as they come due AND # refreshes revert status each cycle

One process under systemd / a Windows service. Also auto-checks reverts.

Built for an enterprise environment

🔐 No stored secrets

Passwords resolve from named environment variables at run time. Config files and the status DB are git-ignored by default.

🔏 Encrypted transport

STARTTLS / SSL with certificate verification. Internal unauthenticated relays supported via auth: false.

🧾 Audit by design

Verbatim .eml archive plus a timestamped SQLite trail of who got what, and who reverted.

🌐 Self-contained

Standard library + PyYAML. No SaaS, no outbound calls beyond your own mail servers.

🧪 Tested

24 offline tests cover config, templating, scheduling, tracking and an end-to-end send.

🧩 Extensible

Send/reply layers isolated behind small classes — an OAuth2 / Microsoft Graph backend drops in cleanly.
